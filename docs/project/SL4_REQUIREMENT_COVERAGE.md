# ServiceLoop — SL-4 Requirement Coverage

**Status:** Development checkpoint on `codex/sl-4-history-recovery`. Independent testing-AI-model verification and owner review remain required; this is not an acceptance claim.

## Implemented

| Area | Coverage |
|---|---|
| Room v6 | Additive v4→5→6 migration, retained migration chains, exported schema, correction content/evidence/provenance fields, recovery adoption token, and live business-change triggers over every business table. Recovery metadata writes do not dirty the dataset. No destructive fallback. |
| History | Global and Customer/Site/Equipment timelines cover records, cancellations, contacts, follow-ups/events, corrections, voids, lifecycle, schedule, and moves. Multi-equipment rows have unique stable keys; contact rows open a read-only contact-note route; event dates use the business zone. Malformed or reversed textual date ranges show field errors and are not applied; Clear removes both bounds. |
| Corrections/voids | Durable resumable workspace edits captured questions/answers/findings, outcomes/work, parts, selected/new correction evidence, public/private notes, captured identity, and service date without mutating prior revisions. Added evidence uses the shared normalized/privacy-safe image pipeline. It is draft-owned while open, cross-resource deleted on discard, and reparented to the committed immutable revision on commit; unselected additions remain internal and report-excluded. Explicit Keep/Cancel/Add follow-up effects commit atomically. Latest counted true→true/true→false/eligible false→true changes update due state and counted revision provenance; older history stays history-only and downstream claims block unsafe changes. Latest counted void reconciles due/provenance; repeated void is idempotent. |
| Reports | Every retained revision/rendition is inspectable by identity, date, kind and status. Missing historical PDFs recreate from that requested immutable revision as a new rendition only when every selected photo still matches its immutable path, size and SHA-256 and remains decodable. Missing/changed evidence fails truthfully. A void notice is a distinct current artifact; ordinary Share is disabled for voided originals, and superseded nonvoid Share requires acknowledgement. Missing/failed reports feed Attention. |
| Lifecycle/move | Reasoned Customer/Site archive/restore, Equipment retire/return, Plan pause/resume/end, dependency review with routable blockers, and reasoned Equipment move. FC-03 blocks a move while a correction is open and preserves old/new historical context while carrying plans/dates. |
| Recovery | Format 2 exports one logical DB snapshot and derives the exact durable file set from it under a shared file-operation gate. Inspection cross-validates DB↔manifest/missing entries, normalizes incomplete availability, stages rows against an isolated copy of the actual Room v6 schema/FK graph, and validates current revision/obligation/template/correction identities before Replace is actionable. Staging is removed and the live dataset is never mutated by inspection. Restore/erase journal every touched and in-progress path; a transaction-specific adoption token distinguishes pre/post DB commit even for the same dataset ID. Startup resolves before seeding/use, or exposes restricted recovery. Owned roots are exactly `attachments/` and `reports/`; successful replacement removes old-only files. SAF selection is bounded while streaming and large reads/writes run on IO dispatchers. |
| CSV | Records ZIP includes README plus customers, sites, equipment, plans, visits, work items, service records, checklist answers, findings, parts, follow-ups, contact notes, changes, history, report index, and attachment index. All/one-customer scope, previous-revision choice, private-field choice, UTF-8 quoting and formula escaping are enforced. Create-only import provides Errors/Warnings/New/Existing filters, saved validation report, explicit duplicate branch decisions, corrected-file restart, atomic import, and results navigation. |
| Erase | Recoverable cross-resource erase stages owned files, commits an empty DB with a new adoption token, and cleans private rollback data before success. Failures/startup interruption resolve to one side or restricted recovery; exported/shared files remain untouched. |
| Navigation | Home Attention, Work → More → History, global/scoped History, record correction/version/void actions, entity lifecycle/move actions, and Settings → Data and recovery are backed by real routes rather than Stage-4 placeholders. |

- Debug unit/build/lint and canonical non-destructive smoke results are recorded in the SL-4 handoff, not inferred here.

## Known verification boundary

This development milestone is IMPLEMENTED and FOCUSED-TESTED, but NOT YET EXHAUSTIVELY VERIFIED. It does not claim SL-4 technical acceptance, owner acceptance, release readiness, exhaustive large-data/accessibility/provider coverage, or B-008 completion. Independent testing must still challenge all recovery crash windows, canonical v4→v6 preservation, schedule/void concurrency, lifecycle races, and real system handoffs.

Stage 5 remains reminders and whole-product hardening. B-008 remains a later Romanian-localized real-technician pilot against a pilot-ready build; it is not satisfied or waived by SL-4.
