## C1 — Dispatch finalization atomicity

**Confirmed and corrected** in `ServiceLoopRepository.finalizeVisit()`. Repository initialization normally inserts the primary Technician identity, but a later missing row is possible and the finalization operation must remain atomic. The old transaction inserted `final_records` and `final_record_revisions`, then returned `Blocked` normally when the Dispatch identity was missing; Room committed that normal return. A retry could then take the existing-record idempotent success path. The identity is now resolved inside the transaction before the first finalization write. Other post-write failures in this path throw and roll back; no remaining normal blocked return follows the first write.

`DispatchPackageTest.missingIdentityBlocksDispatchFinalizationWithoutPersistingPartialHistory` uses an isolated real Room database and removes only its test-owned identity after repository construction. Against the old production code it failed because persisted history changed after `Blocked` (captured in `app/build/reports/refactoring-checkpoint-0/c1-prefixed.log` locally). Against the correction it passes twice while identity is absent, checks the Visit, work, Dispatch bindings, and final history tables remain unchanged, restores the test identity, finalizes successfully, and verifies idempotent retry. `DispatchPackageInstrumentedTest.missingIdentityCannotPartiallyFinalizeDispatchVisit` repeats the failure/retry/success path on the canonical AVD with an in-memory Room database. Existing local and Dispatch success, participation-completion, and recurrence tests remain in the unit and focused connected coverage. ## C2 correction — stale next-date recovery after newer completion edits

**Confirmed and corrected.** The missing-date recovery was an independent `result:nextDueRecovery` coordinator choice whose writer closed over the original `CompletionLine` and calculated date, then retried the unrestricted `saveCompletionDraft()` tuple later. Neither a newer Outcome, fulfillment, Not-performed reason, nor override operation invalidated that closure. Two isolated-Room instrumentation regressions using the actual `ServiceLoopViewModel`, `ServiceDraftAutosaveCoordinator`, and `DraftWriteGate` failed against the pre-correction production code: after a controlled recovery failure and a successful newer Not-performed decision plus reason, generic Retry restored `PERFORMED`; after the corresponding fulfilled-Partly failure and successful Keep-due choice, generic Retry restored true fulfillment. This is controlled source-path evidence, not evidence that an owner dataset was affected. The earlier 46-test follow-up did not cover these supersession sequences and is not retroactively represented as doing so.

`ServiceLoopRepository.recoverMissingCalculatedNextDue()` is now a narrow conditional operation with explicit `Applied(savedAt)` and `Superseded` results. It preflights already-obsolete requests so they do not become artificial write failures, then—after the normal fault-injection/I/O boundary—rereads and validates the WorkItem, owning Visit, local documentation mode, expected Outcome, true fulfillment, captured active obligation identity, plan/obligation eligibility, missing confirmed date, absence of both override raw buffers, captured interval, actual service date, and expected recurrence calculation inside the same Room transaction as the update. The only business columns written are `confirmedNextDueDate`, `nextDueDateCalculated=true`, and the normal null calculated-date override reason; current Outcome, fulfillment, Not-performed reason, manual dates/reasons, raw buffers, Visit lifecycle, obligation, plan, and history are not rewritten. A changed Outcome/fulfillment, manual date, raw override draft, ownership/editability, obligation, calculation context, or prior/duplicate success returns `Superseded` with no mutation.

The ViewModel now gives each WorkItem recovery a narrow request token. Accepting a newer Outcome, fulfillment, Not-performed reason edit, either raw override edit, valid Apply override, or navigation to another Service synchronously invalidates that token and removes only the recovery operation/state. An active obsolete recovery job is canceled immediately and joined before a conflicting canonical completion write proceeds; no coordinator mutex is held while joining. The recovery checks its token before entering the repository and before publishing refresh results. Coordinator conditional choices retire `Superseded` without a false saved timestamp or permanent Retry warning, while refreshing current persisted facts for the still-current context; genuine database/I/O exceptions remain failed and retryable. Raw override text remains independently buffered and exact, including incomplete/invalid strings. Unrelated failed draft operations remain actionable when recovery is retired.

Post-correction regression coverage includes unchanged failed-then-retried recovery for Performed and fulfilled Partly; Not-performed plus reason supersession; Partly Keep-due supersession; valid manual-date/reason preservation; exact invalid and valid raw override preservation with deliberate Apply; a cancellable in-flight recovery gate followed by newer Outcome; changed obligation eligibility; repeated recovery after a saved/manual date; unrelated private-draft failure retention; and retained normal Performed/Partly calculation, Review-link, raw-draft, Service-workspace, and finalization coverage.
