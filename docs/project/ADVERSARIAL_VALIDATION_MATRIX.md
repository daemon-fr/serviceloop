## Fixture and evidence rules

- Mutable/destructive attacks use an in-memory Room database, unique IDs, and test-owned temporary directories. The persistent emulator database is never used for fault injection.
- Repository/domain tests establish persisted business facts. ViewModel tests establish ordering/publication across controlled suspensions. Compose tests establish actual reachable UI behavior. A domain test is not represented as UI or system-handoff evidence.
- `EXISTING` means relevant coverage is present at the starting revision; it does not imply the full attack sequence in this row has already been executed. `ADD` identifies a durable campaign test to add. `RUN` identifies existing coverage to execute in the final gate. `NOT SAFE/AVAILABLE` is reported separately rather than counted as a pass.
- Priority is based on integrity impact and likelihood. Destructive risk refers to the test action; all listed campaign fixtures must be disposable and isolated.
